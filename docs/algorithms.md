# 领域算法与高德接入

## 坐标及复用

基于 `sky1wu/trek-amap-adapter` 提交 `11551251a5bc96cca1c7ea6359c6afee838a109e` 复用 GCJ 转换、区域几何、请求保护、数据 schema、TTL 缓存及坐标回归向量。移除了 Google ID 编码、Google Places 数据结构及 TREK 路由包装。

数据库和应用 API 均使用 WGS-84。高德 Web Service 请求前转 GCJ-02，返回后转 WGS-84；地图绘制时再转 GCJ-02。所有 polyline 均以经度在前的 `[lng, lat]` 保存。香港、澳门和台湾遵循高德的 GCJ 规则，东京、首尔和巴黎保持不变。区域数据来源及近岸容差详见第三方说明。

## 高德 API

| 用途     | Endpoint                           |
| -------- | ---------------------------------- |
| 搜索     | `/v5/place/text`                   |
| 详情     | `/v5/place/detail`                 |
| 输入提示 | `/v3/assistant/inputtips`          |
| citycode | `/v3/geocode/regeo`                |
| 驾车     | `/v5/direction/driving`            |
| 步行     | `/v5/direction/walking`            |
| 骑行     | `/v5/direction/bicycling`          |
| 公交     | `/v5/direction/transit/integrated` |

公交使用推荐顺序、`AlternativeRoute=10`，端点 POI ID 成对传入 `originpoi/destinationpoi`，日期/时间按实际出发时刻转中国当地时间发送。保留所有有效候选；buslines 为一个分段的替代线路，不拼成连续乘车段。空占位 segment 跳过；缺失真实几何的有效方案保留时间信息并标记不可完整绘线。

客户端固定访问高德主机，拒绝重定向；请求超时 8 秒、逆地理编码超时 1.5 秒、单路线总预算 17 秒；响应上限 4 MiB，最多四个并发请求。同一 endpoint 的请求间隔 1100ms，等待队列最多十六项，短期频率限制只重试一次。每日配额和 Key 错误不循环重试。

缓存上限 300 项：输入提示 30 秒、搜索两分钟、详情一小时、城市解析一天、步行/骑行五分钟、驾车/公交一分钟。路线键包含方式、转换后的端点、两个 POI ID 及出发时间五分钟桶；同键请求合并。结构化日志包含 requestId、endpoint、provider、operation、duration、status、cacheHit，不记录 Key、完整高德 URL 或详细坐标。

## 路线与并发

事项顺序过滤 note 后，只有相邻两个实际事项都有坐标才建立 Leg。实际地点缺坐标会阻断该处自动路线并产生警告；同坐标的两个事项自动建立零分钟、明确标识的手动段。

排序/删除在事务中删除过期连接、保留仍然相邻的连接并新增缺失连接。坐标或 POI ID 改动会清理相关旧候选。客户端等操作稳定 500ms 后，从前向后查询受影响的交通段。

网络请求在事务外完成，保存时重新验证权限、Day 版本和 Leg 版本；过期结果返回 409。完整候选替换和选择更新在一个事务内完成。手动选中的路径按线路/步骤指纹尽量保留；路径消失时改用首个有效候选并记录动态。

客户端切换候选不再次请求高德；后续路段的出发时间变化时再按缓存键判断是否需要重算。

## 时间线

内部以相对 Day 零点的秒数推算，避免每段路线向分钟舍入后累积误差。显示时向上取整到分钟。

- 按 Day 开始时间出发，加上交通时间及事项停留时间。
- 每天首个事项不推算到达时间及提前、迟到余量；首项有固定时间时，从该时间安排事项并继续推算后续行程。
- note 不改变所在地点，其停留时间计入下一交通段出发之前。
- 未选择路线、路线失败或手动段缺时长时，到达时间为未知，不能按零分钟移动。
- 固定活动早到则等待；晚到则保留原定结束时间；到达时已结束则从实际到达时间继续并提示错过。
- 明确的时间锚点可恢复后续暂估，但仍说明此前到达时间未知。
- 跨午夜显示“次日”，不强制拆 Day；不自动创建跨 Day 交通段。

## 分摊与结算

金额以整数 minor units 保存，使用 BigInt 中间计算及有理数形式的十进制汇率，处理 JPY/KRW 等零小数币种。金额、汇率转换结果和总账都验证安全整数范围。

equal、percentage、shares 转为整数权重后采用最大余数分配；同余数按稳定 participantId 排序。exact 校验每人原币金额总和等于费用总额。先归一化原币分摊，再按原币承担金额分配折算后的总额；两组分摊均严格守恒。费用整体换汇按 half-up 舍入。

每人余额：

```text
net = paidBase - owedBase + sentSettlementBase - receivedSettlementBase
```

净额为正表示净应收，为负表示净应付。费用页的「建议结算」支持切换「按账目清账」和「简化清账」，默认使用按账目清账。两种方案使用同一套费用和已登记转账，切换只重算建议，不新增结算记录。`calculateBalances` 的可选第四个参数为 `"direct"`（默认）或 `"simplified"`；MCP 的 `get_expenses` 和 `get_balances` 通过可选参数 `settlementMode` 选择方案，并返回实际使用的值。REST 以及未指定方案的 MCP 调用继续返回按账目清账建议。

按账目清账按实际垫付关系逐对计算：每份分摊形成分摊人对付款人的欠款，付款人自己的份额不产生欠款；同两人之间的双向垫付相互抵扣，已登记转账冲抵这两人之间的欠款，多付部分反向退回。双方之间没有费用或转账往来时不会生成结算建议，也不通过第三人转移债务。

建议按金额降序、转出人和收款人 participantId 次序排列，使用整数最小货币单位计算。不以全局最少转账数为目标；个人净额为零仍可能有对不同成员的应收和应付，包括循环垫付。结算不计入旅行总支出；费用修改后已转账记录继续存在，历史转账即使没有关联费用也会计入双方往来，必要时产生退款建议。

简化清账将全体成员分成净应收和净应付两组，各按绝对净额降序、participantId 次序排序，使用双指针贪心匹配转账。允许跨账单转移债务，也能抵消循环往来；不保证数学上的最少转账笔数。按简化方案登记转账后再切回按账目方案，可能看到净额相抵的双方往来，页面会在全员净额为零时说明两种方案的差别。

## 协作与持久化

SQLite 开启外键、WAL 和 5 秒 busy timeout，业务事务使用同一连接；Drizzle 管理 schema、迁移及认证适配，业务事务使用参数绑定的 SQLite 语句。SQL 表名和列名来自服务端固定代码，不接受请求传入。

所有业务修改与 Activity Log 原子提交。SSE 每秒查看新的活动序号，每十五秒发心跳；连接及重连后客户端获取最新快照，无需事件溯源。每次轮询重新校验成员状态及有效会话，移除成员时关闭连接并清除客户端页面数据。


## 多人路径、嵌套与跨日集合

`plan-graph.ts` 将行动段按参与者展开为个人路径，再汇总为有向无环依赖图。组内行动段通过 `branchId` 归属上级分组；集合点属于上级同一层安排，个人路径会跳过尚未参加的共同事项，支持各组在不同地点分批会合。校验成员子集、重复分配、循环嵌套、重叠行动段和互相等待的环，所有结构写入在 SQLite 事务内完成。

`trip-timeline.ts` 使用日期位置生成全程时间偏移，每个人保留自己的时钟。只有明确的 `wait_all` 会合点才按实际参加者的最晚到达时间同步；任一人时间未知时保持未知。固定活动保留团队约定时间，同时保存每个人的实际预计开始、离开与迟到；普通日界不会将已延续到次日的延误重置到更早时刻。时区到 ISO 的转换仍使用既有 Luxon 规则。

固定集合配置 `catchUpItemId` 后，预计迟到的人保留出发前状态，改走从原出发点到后续会合点的独立 `catch_up` 路线，跳过中间事项。错过火车、飞机等固定班次仍保留未知后续时间，不假设成功抵达。地图个人视图使用实际采用的路线 ID；所有人视图保留各人的到达差异。

路线按依赖次序计算，路线所属日期为到达事项日期，起点可在前一天。普通事项和独立交通使用相同端点规则；公共备注耗时在分开前或集合前正确进入时钟。路线候选仍由高德返回，跨日和嵌套不产生伪造道路几何。

批量分组与整段复制/移动检查行程全部日期版本后一次提交。复制为事项、分组与路线候选生成新标识并重映射内部引用；移动保留标识并同步账单日期。日期范围不足、其他行动段的引用失效、权限或版本冲突均回滚整个操作。
